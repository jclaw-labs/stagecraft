# Deep-review orchestrate

One session drives the whole review cycle. A fresh subagent reviews the PR, you address what it found, and the two alternate until the loop stops on its own.

You are the orchestrator and the addresser — and you may hand the addressing pass to a subagent (step 3). The reviewer is a subagent, and it must never be you — that separation is the only thing here that produces value.

**Don't start this loop on your own** after opening a PR. It runs up to five review rounds, the first with two reviewers, and five addressing rounds, and it belongs to the user to ask for.

## Arguments

`/deep-review-orchestrate` — loop on the PR for the current branch
`/deep-review-orchestrate 136` — loop on PR #136

## Run it to the end. Return once.

The loop is **one long-running task, not a series of check-ins.** Start it, run every round, and come back when it's finished. The ordinary "agent is done" notification at the end of your turn is how the user learns the PR is ready for their eyes, and that only works if you return exactly once.

So don't ask the user which option to take between rounds. Every decision the loop needs is already written down: the stopping rule in step 4, the escalation list below, and `address-deep-review` for which findings to take. A mid-loop question turns a task the user walked away from into one that has been sitting waiting on them, which costs them the thing the loop was for.

- **Use your judgement and keep going.** When a call is genuinely yours — a finding to decline, a round to run again — make it, record the reasoning, and move on.
- **Report as you go, but never ask.** A one-line summary per round costs the user nothing, because it doesn't hand control back. A question does.
- **Return early only to escalate.** Each condition in the escalation list ends the turn with a report, and that's a finished task too, not a check-in. Someone else's uncommitted work is the one stopping reason that isn't on the list, because it can turn up at any moment rather than at a round boundary.
- **Keep every reviewer in the foreground** (step 1), so the turn ends when the loop does rather than while it's still running.

The final report is the deliverable and the only thing they'll read. It carries what happened each round, what you pushed, whether the loop stopped clean or escalated and which condition fired, anything left for them to decide, and the PR URL.

## Why the reviewer has to be a subagent

An agent cannot review code it just wrote. It reads the diff as it meant the diff, so the gap between what it intended and what it typed is exactly the gap it can't see. A subagent starting from nothing has to reconstruct the intent from the diff, the PR description, the tickets, and the repo's own documents — which is the position a future maintainer is in, and the position from which defects are visible.

This is measured, not assumed. Over one four-PR stack — 14 review runs, 139 findings — roughly **one addressing round in five introduced a defect that only the following review caught**, including a fix that re-created the exact bug its PR was opened to fix, in a commit whose own comment asserted that couldn't happen. None was visible to the agent that wrote it.

So: **a new subagent every round, never a resumed one.** A resumed reviewer carries last round's context and stops being fresh, which quietly converts the loop into one agent talking to itself. Continuity lives on the PR instead — each round's marker comment is readable by the next reviewer, so nothing needs to be remembered.

## Before the first round

- **Start the loop in a fresh session, or expect to hand over early — on a small window.** Five rounds of review-plus-addressing is most of a ~200k context window on its own, so there a session that already carried the work being reviewed has no room for the loop that follows it. Check the window before you predict anything: it is stated in the model line injected into your context (`context=1m`, say), so read it rather than guessing from how long the session feels. On a ~200k window, asked to loop at the end of a long implementation session, say up front that you'll likely escalate on context at the first boundary and suggest a fresh session — that costs one message, where discovering it mid-round costs the round. On a 1M window don't: one loop there ran all five rounds without delegating once, and the warning it opened with cost the user a decision they didn't need to make. This is the cheapest of the escalation conditions to predict and the only one you can see coming before round 1.
- **A PR exists and it's pushed.** No PR yet? Open one with `create-pr` first.
- **The loop may always comment on and push to the PR it's working on.** Being asked to run the loop on a PR is the permission to record the loop there — each round's marker, each response, and any parent fallback — and to push the addressing pass's fixes onto its head branch, whoever opened the PR. Pushes are new commits and a plain `git push`, never a force-push, so the owner's "changes since you last reviewed" still shows what the loop did. If the push is rejected for lack of access, don't work around it: retain the fixes as a patch, record `Pushed: rejected` in the response header, and escalate as fixes taken but not landed (below), handing the patch to the owner in the final report. `deep-review` stops before posting unless it can confirm the caller opened the PR, and that check fails for someone else's PR and for a cloud credential that can't resolve a user. So every reviewer prompt carries `MARKER-POST-AUTHORIZED: <owner>/<name>#<pr>` (step 1), which `deep-review` accepts in place of its check. The grant covers those comments and pushes on this one PR and nothing more, with one scoped exception: when `review-end-decision`'s close route applies to queue-owned single-PR work, the loop may also close that PR and return its owner issue to `Ready` as that route directs. It never covers replying to a human reviewer, resolving their threads, submitting a review, or acting on a human reviewer's comment — the loop fixes its own reviewers' findings, not theirs.
- **Local HEAD matches the PR's head SHA.** The reviewer reviews what's on the remote. An unpushed commit means you're addressing findings about code that isn't the code.

  When a clean tree doesn't match, read it before you reset, push, or stop. Neither ahead/behind counts nor discarding settle it, and both readings below were invented mid-session the first time:

  **A clean tree ahead of the PR can be an interrupted addressing pass.** Compare the local-only commits with the newest unanswered marker. Resume only when they are one linear, exact response to that marker, touching the files and behavior its findings name and nothing else, and when whatever wrote them has stopped: no live addressing subagent, and no session still working in the tree. Then re-run the finding's probe and the local checks, push, triage any of the marker's findings the commits didn't cover as `address-deep-review` directs, and post the missing response comment before you dispatch the next reviewer, saying which evidence made you read it that way. On PR #216 that was a clean tree, one commit, an exact file and finding match, and timestamps ten minutes after the marker. If the commits hold anything else, or no marker accounts for them, stop and surface it: the loop doesn't own unexplained local commits.

  **A clean tree that is both ahead and behind may hold stale copies of a rebased PR.** Fetch the head branch first (`git fetch origin <head-branch>`), then run `git cherry origin/<head-branch> HEAD` over the local-only range. When every row is `-`, the local commits are patch-equivalent to commits already upstream, so `git pull --rebase origin <head-branch>` may align the tree (name the branch: a `review/pr-<pr>` tree tracks nothing, and a bare pull fails there); check afterwards that the full local and remote SHAs match. `local-config-worktree --review` refuses both states the same way, as commits it didn't record, so pick the reading by the tree's shape, not the refusal: ahead only is the interrupted-pass reading above, ahead and behind is this one. Any `+` row is local work nobody explained: stop and surface it rather than rebasing or discarding it. On PR #337 a tree one ahead and five behind looked like a third party's work, and was the pre-rebase copy of the PR's own commit.
- **The working tree is clean**, and it's a tree nobody else is typing in — a worktree or a claimed slot, not a checkout someone has open. You need it clean to commit from, and you need it quiet because after the fact a reviewer's probe and somebody's in-flight edit look identical.

  In local-config, make that tree with `WT="$(local-config-worktree --review <pr>)"`, not branch-name mode. It fetches the PR's own head into a `review/pr-<pr>` branch, hands back the same worktree while that head is unchanged, and refuses a dirty review worktree or a review branch with commits it didn't record. Branch-name mode checks out whatever local branch has the name, and on an umbrella issue reused across PRs that was an older PR's branch, four commits ahead and 84 behind the one under review. `review/pr-<pr>` tracks nothing, so push the addressing pass to the PR's head branch by name: `git -C "$WT" push origin HEAD:<head-branch>`, with the branch from `gh pr view <pr> --json headRefName`. That is still a plain push, never a force-push.

  **Getting that tree is the one place a blocking question is correct**, and it doesn't contradict the run-to-the-end rule above, which governs decisions *inside* the loop. When the only tree to hand is one somebody else may be using, taking it over is the user's call and nobody else's, so don't pick one and don't start the loop in a tree you shouldn't be in. Ask before your first dispatch or not at all — which is round 1 on a fresh PR, and whatever round you start at when you pick up someone else's loop. Once you're dispatching, the same question costs them a loop they'd walked away from.
- **Get the round number from `review-loop-state <pr>`**, and pass it to each reviewer rather than letting the subagent count for itself. It sits next to this file, so a vendored copy of this skill carries it. Resolve it in this order: `bash <dir>/review-loop-state`, where `<dir>` is the directory of the path you read this SKILL.md from; then `review-loop-state` on PATH; then `bash .claude/skills/deep-review-orchestrate/review-loop-state` in the project. The skill's own directory comes first because that is the copy written for the instructions you are following — an install under `~/.claude/skills` has no project-relative copy, and a PATH copy can be a different version. Run a file path through `bash`, because a checkout that lost the exec bit would otherwise fail with a permission error that reads like the file being missing. It needs `jq`, and either `gh` or curl with a token in `GH_TOKEN`. It uses `gh` when that is installed, and either way falls back to REST when GraphQL is refused, as a cloud session refuses it. It also reports the cap and any must-address a previous round refused, so one call answers the three questions this section used to work out by hand.

  **Pass `--repo <owner>/<name>`.** Without it the script has to work the repo out from your checkout — `gh repo view` where `gh` is installed, the `origin` URL on the curl path — so either way it needs your shell's cwd to be inside that checkout, and this loop `cd`s to `/tmp` constantly for `gh` work. The bare form then fails mid-loop with `cannot resolve repo`. You already know the repo, so name it.

  **A `Forbidden` from it is the sandbox, not your access and not a stale binary.** Re-run with unrestricted permissions. This is worth stating alongside the cwd problem because the two are independent and each is fixed by the other's non-fix: `--repo` does not dodge the sandbox — the REST reads are blocked too, not just the `gh repo view` that resolves the repo — and unrestricting permissions does nothing about the cwd. Expect to hit them in separate rounds and don't let fixing one convince you the other can't happen.

  Don't recompute it in your head. Four review rounds on this skill filed nine findings and every one was the same defect — arithmetic over comment text, done in prose, done wrong. The round number is the larger of two figures, because each misses a different round: the highest run a marker names misses a round whose marker was denied, and the highest run a response names misses a round whose response never posted. Counting comments that merely *contain* a marker string is worse than both, since any review discussing the counting rule quotes it. That logic now lives in the script with fixtures for each of those cases, where a wrong answer fails a test instead of shipping.

  **A write-stopped round is invisible to the script.** It posts neither a marker nor a response, so the script's figure doesn't advance and never reaches the cap. Once any round in this session is write-stopped, number each later round as one more than the last round you dispatched, or the script's figure if that is larger. Apply the cap to that number too. Put the count in the handoff, because a resuming session reading the PR will see fewer rounds than happened. A session resuming a loop it didn't run can't see that count unless the handoff reached it, so also list `<common-dir>/deep-review/<pr>-run*` (the directory the write-stopped bullet in step 3 keeps) and number past the highest run found there too. Read those files for any round the PR doesn't show.

  It reads a run number rather than counting markers because a round can legitimately have two of them, and counting inflated the number permanently once that happened — then the loop stamped the inflated number into every later round's own comments, so nothing downstream could recover it. The run number comes only from each comment's own header. With HTML comments removed, that is the text before the first `</sub>` when the comment opens with `<sub>`, and otherwise its first non-blank line. It reads `re-ran (run N)` in a marker, also with a comma-led note inside the parens (`re-ran (run 5, the cap)`) or as a title that opens the header (`# deep-review, run 5 (final)`), and `responded to run N` in a response. A review quotes other rounds' headers in its prose, and a first-run header names no run, so reading past the header took a quotation as the run. A marker naming no run is run 1.

- **Check whether another loop is already running, before your first dispatch** — round 1 on a fresh PR, and whatever round you start at when you pick up a loop someone else began. Two loops on one PR is not hypothetical: it has happened, both numbered themselves run 1 against the same head, and the duplicate marker permanently inflated the round counter — that PR escalated at "5 of 5" having reviewed three distinct code states. Nothing else in this file looks for another loop numbering itself the same round as you: the checks below compare *heads* between rounds, which catches a push you didn't make without telling you who made it.

  **An unanswered marker is the state to look at, and it is ambiguous.** A marker with nothing under it means either a peer has finished a review and is addressing it, or some loop was interrupted between its review and its addressing pass — which this file documents twice, at the backgrounded-reviewer resume in step 1 and at the context escalation below. If you dispatched that review yourself, it's yours: address it. If you didn't, nothing on the PR tells you which, so say which reading you took and why instead of stopping flat. Addressing a review that was waiting anyway is the recoverable error; refusing to resume a handover is not.

  Neither age nor author discriminates, and no tool answers it for you. Two IDE loops on this Mac both post as me, and the PR body's background-agent footer records who *opened* the PR and never expires, so it reads "an agent owns this branch" forever, merged PRs included. `review-loop-state` reports numbers rather than order, and `marker_rounds > named_rounds` is not the proxy it resembles: a response naming run *n* beside a marker for run *n+1* gives equal counts on an unanswered marker. `marker_named > named_rounds` does detect that one exists, being the highest run a marker names against the highest a response names — but it still can't tell you whose it is, which is the question here. A run that two markers name is reported directly: `duplicate_marker_runs` in `--json`, and a `duplicate marker  run N has M markers` line in the text output. Two reviewers read that round. What it means depends on which run. A duplicate on the run you are about to answer, `rounds_complete` and labelled `the run being answered` (`current` in `--json`), is live: if you dispatched only one of them, a peer loop is running, so stop and report it as a peer loop (an escalation, below). If you dispatched both, the round's response answers every marker for that run, not only your own reviewer's, and the tool won't report a clean stop on that run at the cap, since it can't tell whether the response covered both. When both are your own reviewer's on the same head, usually a re-post after a post that looked failed but landed, the way out is `deep-review`'s fold rule, which you make as the owner of both reviewers even though the marker's note reserves it to a reviewer: append the second below the first's `</details>` without its marker line, delete the separate comment, answer both passes in the response, and re-run `review-loop-state`, which then counts one marker. A duplicate on an earlier run is history: check that a later response answered that run's findings, and move on. Read the order yourself with `gh api repos/<owner>/<name>/issues/<pr>/comments --paginate --jq`, classifying each comment by its first non-blank line — "under" means later in that flat list, since issue comments don't nest — and keep `-f`/`-F` out of it per the reply-guard bullet below.

  Say plainly what none of this catches. A marker is written at the *end* of a review pass, so a peer inside its first pass leaves nothing on the PR at all, and that holds at every round rather than only the first — which is also why a response with nothing under it is ambiguous in its own right, between a handover and a peer about to dispatch. Once a peer's marker exists `review-loop-state` counts it and you number yourself the round after, so a duplicate run number can't arise that way. The simultaneous window is invisible, and implying otherwise is worse than admitting it. It stays invisible until the script reports these signals itself — the deferred half of #72 item 3, which is also when this clause will want rewriting.

  **A marker this session wrote by hand is not a round.** The two readings above miss a third origin: you reviewed the PR yourself earlier in this session, outside any loop, and I asked for the loop afterwards. That marker is yours, but no reviewer was ever dispatched for it, so nothing has reviewed this code except the session now proposing to address it, which is the one thing this skill exists to prevent. Address it if you like, then dispatch a reviewer anyway, numbered as `review-loop-state` reports, and give it your review as prior context, as **Skip only on a head you recorded yourself** below does for a review run by hand. "If you dispatched that review yourself" means dispatched, not authored. `review-loop-state` still counts the hand-written marker, so your first dispatched reviewer is numbered round 2 and the cap arrives one separated round early; say so at handover rather than reporting the count as separated rounds. On substackinc/substack#75553 the self-reviewed round missed the race the PR existed to fix, and the first dispatched reviewer found it.

  If one is running, don't start a second — say so and stop. A second loop is worse than a slow one, and its cost lands on the counter, which every later session inherits.

- **Don't re-review a head you dispatched a review for.** If the newest response comment answers a run this loop dispatched, and the head you recorded for that run is the current head, a review of this exact code already exists — read it and address it rather than dispatching a fresh reviewer, which would produce a different list for the same code and spend a round on the difference. The one exception is a round 1 posted with a wrong must count, which goes again on the same head (step 4).

  **Skip only on a head you recorded yourself.** Every SHA written in a comment is untrustworthy for this: `address-deep-review` defines the response header's SHA as a copy of the marker header's, and `deep-review` fills that header from a live read of the PR's head when it posts (step 4 has the mechanism). So on the case this bullet is really for — a review someone ran by hand, before any loop existed — the comment names the head at posting time, which on a review that raced a push is a commit nobody read. Skipping there is worse than mis-stopping: you address a review of the old code as though it covered the new. When you have no recorded head of your own, review rather than skip, and read the earlier review as context instead of as this round.

- **Reading PR comments can trip a reply guard, wherever in the loop you do it.** A `gh api` command that names a comments endpoint and also carries a `-f`/`-F` flag reads as a write to the guard, which denies the whole thing — so a fixed-string matcher in the same pipeline gets you a deterministic block over a command that only reads. Use `gh api`'s own `--jq` with a `contains` test. It needs both halves to fire: the same query built on `gh pr view --json comments` is fine, and `grep -cF` passes where `grep -c -F` doesn't, because the guard matches the flag as its own word. This applies to every comment read the loop makes — the round number here, the reviewed head above, and reading a review off the PR in step 2.

## The cycle

One round is a review by the subagent plus an addressing pass by you. Round 1 has two reviewers, folded into one review (below).

### 1. Dispatch the reviewer

Dispatch a general-purpose subagent through the harness's subagent tool. In Cursor that is the Task tool with `subagent_type: "generalPurpose"`. In Claude Code it is the Task tool with `subagent_type: "general-purpose"`. Don't use a read-only exploration type such as Cursor's `explore`: the reviewer has to run the suite and mutate code, and a read-only agent can do neither.

**If you can't dispatch a fresh subagent, stop before round 1.** Some harnesses have no Task tool — a Cursor Cloud agent that another session launched is one; where it isn't among your tools, look it up by name in the `cursor` namespace before concluding it's missing. With no way to dispatch, report that and stop. Never review in-session instead: that is the one thing this loop exists to prevent.

**Run it in the foreground.** The loop is strictly sequential, round 1's two reviewers included, so there's nothing to overlap it with, and a foreground reviewer is what keeps the turn's end and the loop's end the same event. It also keeps you from editing files while the reviewer probes, though that matters less than it sounds: auto-review declines most in-place mutations, so reviewers work in a throwaway clone anyway, except where the suite needs the real tree.

**Round 1 gets two reviewers.** Two reviewers following the same skill disagree more than any rewording of it changes, and the defects that survive to merge are usually already there in round 1 (#927). So round 1 dispatches two, one after the other, on the same recorded head in the loop's own tree, and neither posts anything: you post one folded marker. Running them in turn keeps their probes out of each other's way and keeps the tree whose dependencies the suite needs, and since nothing is on the PR yet, the second can't read the first's review. Every later round, and a certification pass, has one reviewer who posts its own.

- **Give each the round-1 prompt, not step 1's as written.** Start from the prompt below and change it in four places. Drop the `MARKER-POST-AUTHORIZED` line and every sentence about writing, posting or indexing the marker: the Tools line's instruction to post with `gh`, the body-file path, the `MARKER-*` lines, the post-then-index request, and "Your only durable outputs are the marker comment and your final message". Invoke `deep-review` with `--return-only` instead, and say that for this pass the loop's tree is the disposable checkout `--return-only` asks for, to be restored as the prompt says. Ask it to write its complete review to its own pass file, `/tmp/deep-review-pass-<pr>-run1-<short-sha>-a.md` (`-b` for the second), as its last write, after the tree is restored, and return the same review as its final message; say to write nothing under `/tmp/deep-review-marker-*`. Everything else stays, including the head, the budget, the tests and the clean-tree check. Before dispatch, grep the `deep-review` copy you pass for `--return-only` as well as for the grant.
- **The pass file is round 1's durable copy.** Before dispatching a pass, check its path. A file there that none of this session's passes wrote was left by a peer loop or an interrupted round, which is the fold file's case below, so report it the same way and stop. Count a pass file as a review only when it carries `deep-review`'s section headings. Nothing is on the PR yet, so where step 1 says to read a backgrounded or quiet reviewer's review off the PR, or to check the PR for its marker before replacing it, read that pass's file instead. A pass file that is there is the review even if the final message never arrives; one that isn't is a pass still running, and the never-replace rule holds.
- **Check each pass like any round.** After each returns, run step 2's SHA and tree checks before dispatching the next, so B starts on the tree A was handed. A pass with neither a complete review in its final message nor a pass file holding one didn't happen: re-dispatch that pass alone, as step 2 says for a whole round, and never fold or post a single review as round 1. If it left a pass file without those section headings, move that file aside first (`mv <file> <file>.malformed-$(date +%s)`), so the new pass writes a fresh one and the fold can't read the old.
- **Fold them into the round's body file yourself.** Call the first pass A and the second B. If a file is already at `/tmp/deep-review-marker-<pr>-run1-<short-sha>.md` and you didn't write it in this session, another loop or an interrupted fold wrote it, and neither is safe to post over: report a peer loop (an escalation, below), name the file's path in the report so whoever owns the loop can confirm no peer is running and delete it before the round is re-run, and stop. Otherwise write it in `deep-review`'s marker format: A's complete review inside `<details>`, then B's below A's `</details>`, per `deep-review`'s fold rule, numbering A's findings `A1…` and B's `B1…`. Write the `<sub>` header counts as the union, in exactly `deep-review`'s shape with nothing added inside the parentheses: `<N> findings (<M> must-address)` counts a finding both passes raised once, at the higher severity, and counts two findings separately when you can't tell they are the same. `review-loop-state` reads must-address only from that header, so without this a must only B raised can't hold the stop.
- **Post it once, the way step 2's fallback does.** Check it with `review-loop-state --check-body <file> --expect review`, for `deep-review`'s section headings. That check also passes a header annotated inside its parentheses, which `review-loop-state` then reads as no must count, so check the header line as well: `grep -m1 '<sub>' <file> | grep -cE ' — [0-9]+ findings? \([0-9]+ must-address\)'` must print 1. It reads only the first `<sub>` line, so a header quoted inside a review can't pass or fail it. Then run `deep-review`'s standalone `--body-file` command in its own call. Step 2's `MARKER-POST-STATUS` and `MARKER-HEADER` checks don't apply here, since you wrote the file and no reviewer tried to post. If the post is denied, the round is write-stopped (step 2), and both reviews go in the next prompt and the handoff. Re-run `review-loop-state --json` and require `duplicate_marker_runs` empty and `latest_run_must_address` equal to the union's `M`. A duplicate marker is the peer condition in the escalation list. A wrong must count with no duplicate means the record you posted is corrupt: handle it as step 2's corrupt record (say so in the response, don't edit or re-post), address round 1 as usual with a row for every must-address finding in the union, and run round 2 even if round 1 pushes nothing, as step 4 says.
- **Nothing reaches the PR until the fold posts.** A round 1 interrupted before then left no marker, so a resuming session re-dispatches it (step 2's "that round didn't happen"), unless a pass file or the fold file is already written: the resuming session didn't write it, so the checks above stop on it. Both full reviews pass through your context once; that is round 1's price, and later rounds return the index as usual.

The folded round is one round: one run number, one response answering both passes (`A1 · B2` row ids, per `address-deep-review`), and one step toward the cap and the escalation list.

**If a reviewer ends up backgrounded anyway** — the harness forces it in some modes — then end the turn, because that is the only way its result comes back and polling for it is forbidden. Say in that turn that a reviewer is still running, so the done notification isn't read as the loop finishing. When you pick the round back up, expect that its final message may never arrive at all: read the review off the PR instead (step 2).

**Never replace a reviewer you think has died.** Completion notifications are unreliable in both directions — some never arrive, some arrive an hour late, some arrive twice — so "it's been quiet for a while" is not evidence. One loop diagnosed a reviewer dead from its transcript file sitting unmodified for 26 minutes and launched a duplicate; the original had in fact finished and posted its marker, and the duplicate would have posted a second marker for the same head, which is the thing that corrupts the round counter for every later session. Transcript mtime is not a liveness signal — the file doesn't flush continuously — and there isn't a good one, which is the actual reason for the rule. If you genuinely cannot wait longer, check the PR for a marker naming this round before doing anything else; a duplicate reviewer is worse than a slow one.

**Give the reviewer a budget, because once it's running you can only wait.** That's the other half of the rule above: an unbounded reviewer can spend the whole loop's time, and the rule leaves you no way to take it back. One ran nine hours and returned nothing. Re-dispatched with a 90-minute target, a five-mutation ceiling and measured suite times, it finished inside them and produced that loop's best round. Fill in the budget block at the top of the prompt every round. Take the suite times from your own recent runs: under peer-agent load a reviewer can't measure them in a way it should trust, and without them it reaches for the full suite to check a claim one cheap suite would settle.

**Make sure the suite can run on this head before you dispatch.** A reviewer is read-only, so a head whose tests refuse to run gets a review established by reading alone, and the mutation probes that catch what reading misses never happen. In a repo with a test-database gate, run one of the PR's own specs from the tree first; in Substack, `stest` refuses with "Rebase and re-run" when the branch lacks a migration the master-pinned template has. On that refusal, bring the branch up to date now through [`refresh-stack`](../refresh-stack/SKILL.md), which pushes a lone branch as a stack of one and is the path the force-push guard names for a master update. Verify tip against tip as the rebase bullet in step 4 says, and dispatch on the new head. Moving the head here doesn't spend a round, because no reviewer has read the old head in this round; record the SHA below only after it. A certification round is the exception: it may not move the head (see **Certification after a cap handoff**), so tell its reviewer the suite won't run and why. On substackinc/substack#77268, round 7's reviewer hit that refusal, ran nothing, and the addresser rebased afterwards, so the response had to explain a SHA the reviewer never saw.

**Hand the reviewer the `deep-review` beside this skill, by path, and check it carries the grant.** Use `<dir>/../deep-review/SKILL.md`, where `<dir>` is the directory you read this SKILL.md from, the same rule that resolves `review-loop-state`. That is the copy written for this loop's posting grant. A project can vendor its own `.claude/skills/deep-review`, and that copy can be a team-shared version that has never heard of `MARKER-POST-AUTHORIZED`; in Claude Code it also shows up as a project skill with the same name, so a reviewer told to "use the deep-review skill" can load it without anyone choosing it. A reviewer following that copy ignores the grant and stops before posting on any PR the caller didn't open. So before dispatch, run `grep -c MARKER-POST-AUTHORIZED <path>` on the copy you're about to pass. If it finds nothing, don't dispatch: stop and say which copy you resolved and that it lacks the grant. Five Substack loops each had to work this out by grepping both copies, and three first leaned toward the project's copy.

**When the PR edits a skill or an AGENTS.md, the reviewer still follows the installed copies, and reviews the branch's copies as part of the diff.** The installed `deep-review` and AGENTS.md under `~/.claude/skills` and `~/.agents` resolve into the main checkout, so they are older than a branch that edits them even when main is fully current. That is the copy the reviewer should follow: a reviewer that followed the branch's rules would let a PR rewrite its own review. But a reviewer that reads only the installed copy can't see the change, and may review the old text as if it were the PR's. So list every file the PR changes under a `skills/` directory and every AGENTS.md it changes, taken from the PR's own file list (`gh api --paginate repos/<owner>/<repo>/pulls/<pr>/files --jq '.[].filename'`). Don't diff against a local base: `local-config-worktree --review` fetches only the PR head, so a stale `origin/main` makes the three-dot diff list skills from main's own commits that the PR never touched. Put each file in the prompt's "Guidance this PR edits" block twice: its absolute path in the branch worktree, which the prompt says is diff to evaluate and never rules to follow, and its absolute path in the main checkout, which is the copy to read whenever the reviewer's rules send it to that skill or file by name. The second path is needed because `.claude/skills/<name>` in a review worktree resolves to the branch's copy, so a reviewer sent to an edited skill by deep-review or AGENTS.md would otherwise load the PR's version. Write `none` there when the PR edits no guidance, so the reviewer doesn't go looking.

**If `review-loop-state` reports PR metadata synchronizing, wait and re-run before you record the SHA or stop.** Its text output says so on the `head` line (`head  PR metadata synchronizing -- branch at …, PR still names …; wait and re-run`), and `--json` sets `metadata_synchronizing: true`. The branch has a newer commit than the PR's own metadata names, and that metadata can lag a push by several minutes. It leaves `head` without a SHA on purpose, so don't substitute `branch_head` or `pr_head` for it, and don't hand a reviewer an empty SHA. Re-run it every minute or two. If it is still synchronizing after about 15 minutes, stop at this round boundary and report that the PR's metadata never caught up, naming both heads it reported, rather than waiting on it indefinitely.

**Record the current commit SHA in full before you dispatch, and put it in the prompt.** Steps 2 and 4 both need it: it's how you tell afterwards whether the reviewer stayed within its write-denial, and it's the operand of the stopping test. Record all forty characters, so that comparison is against the API's own format and needs no normalising — an abbreviated one has to be resolved first, and `git rev-parse` on a short SHA it doesn't have exits with `fatal: ambiguous argument` while still printing the input back, which reads as success. Telling the reviewer which commit it's on also gives it something to check itself against.

Don't ask it to write that SHA into its marker header instead of the one `deep-review` specifies. The prompt tells it to follow `deep-review` exactly, so an override in the prompt is a contradiction the reviewer has to resolve, and it resolves toward the skill — the loser being the header, silently. You don't need the header: the SHA you recorded is the operand of the stopping test. (Teaching `deep-review` to prefer a SHA it was handed would fix the header too, for every reader of it rather than just this loop, and that's a change to a shared skill rather than to this one.)

**Say how to run the tests, and warn the reviewer off guessing.** A fresh subagent told to "run the suite" will improvise an invocation, and where a wrong guess is destructive rather than merely wrong that costs more than the round — a bare test-runner call can fall back to the development environment and wipe the local dev database. Look the command up in the repo's own instructions and pass it in, rather than writing the obvious invocation yourself: a repo may run one suite only through a wrapper and deny the direct call by hook. Give the one-suite form, plus the full gate where the repo has one a reviewer should run, and say the full gate is for claims that span suites: hand over only the full gate and "don't improvise" forbids the cheap run the budget asks for. Before you tell the reviewer the diff has no tests, search the test tree at the recorded head for the changed modules' names (`git grep -l <Name> <head> -- <test dirs>`), as its own command so the answer isn't buried in other output, and put that search in the prompt next to its result. If you can't tell, say what you searched and let the reviewer decide. A wrong "no tests" sends the reviewer to probes when a suite would have settled the claim: on substackinc/substack#78613 the search had found the SSR test, under an unrelated error in a combined command, and the prompt said there was no suite anyway.

**List the tools the reviewer will run, by absolute path.** Its shell is not yours, and twice a prompt assumed something was on its PATH: first `gh` for `gh pr comment`, then `review-loop-state`. Resolve each one before dispatch with `command -v`, and fill the prompt's Tools block with what came back. Write `not available` for one that resolved to nothing, so the reviewer reports the gap instead of guessing a path. List only what the round runs: since #783 the reviewer checks its body file with deep-review's own `awk`, so `review-loop-state` isn't one of its tools. The test runner isn't a Tools entry either: it stays on the prompt's "Run the tests with" line. A runner can be a shell function, as Substack's `stest` is, and `command -v` then gives back a bare name, or nothing in a shell without the function, which would mark it `not available` when AGENTS.md says not to conclude that. The `gh` entry says whether `gh` exists and where; the marker post itself keeps deep-review's bare `gh`, because `guard-no-reviewer-reply.sh` allows that line only in that shape and denies `DEEP_REVIEW_SKILL=1 /path/to/gh pr comment`.

### 2. Check what came back

- **The review is on the PR; the final message is the index to it.** Every review used to come back in full, which put a second copy of text already durable on the PR into the one context that can't be replaced: on PR #129 three rounds cost 72,744 characters of review alone, and the loop escalated on context at 3 of 5 even with two addressing passes delegated. So the reviewer returns the marker URL, a findings table, its verdict and its baseline, and you read the marker when you need a finding's evidence — which you will for anything you're about to act on or re-derive. A round you triage from the table without opening the marker is a round whose findings you haven't verified: the table tells you which findings to open, not whether to open any. If the marker didn't post, the round's body file is the review when it passes `review-loop-state --check-body <file> --expect review` and carries the section headings `deep-review`'s format calls for, which is the usual cloud case, where `gh pr comment` can't post and every round is `parent-fallback-ok`. Only when the file is missing, fails that check, or lacks those headings must the final message carry the whole review, and a summary there isn't reviewable. If the subagent described a review it should have pasted, read the body file at the round's path rather than dispatching a second reviewer.

  **It will usually tell you it complied.** An assurance that the marker posted, or that a pasted review is in full, is what you'd get either way and isn't evidence — one reviewer returned a summary under the sentence "the review is above in full". Check the marker with `review-loop-state` (below), and for a pasted review look for the section headings `deep-review`'s format calls for, not for the claim.
- **The marker comment posted.** If it didn't, the loop still runs — you hold the round number and the review text — but the PR has no record of the round. After classifying the failure below, record that gap in the response comment when writes remain open or in the retained response when they do not. In either case, paste the review into the next reviewer's prompt so the history it would have read isn't lost.

  **Read the reviewer's marker-post status before writing anything.** `MARKER-POST-STATUS: canonical-command-denied` makes this round write-stopped: do not post the marker on the reviewer's behalf, and do not post the later address response. Carry the full review and eventual response in the next reviewer's prompt and the final handoff instead. The same canonical command is not a fallback for its own deterministic denial.

  **Use parent fallback only when the failure is safe to correct.** `MARKER-POST-STATUS: parent-fallback-ok` covers a read-only credential, a missing comment-write tool, or an explicitly reported noncanonical attempt whose shape you can distinguish from the canonical command. If the reviewer omitted the status, require equally clear evidence of one of those cases; an ambiguous hook denial is not permission to write. Getting the record onto the PR is what makes round *n+1* cheaper than round 1 — without it every later round is blind to its predecessors, and a resuming session sees a loop that never happened.

  Two things the header alone won't give you, and both fail silently. The comment has to **open with `<!-- deep-review-marker -->`**: `review-loop-state` reads the first non-blank line, so one opening with the `<sub>` header counts as no marker at all. Your own response comment names the run, so the round count survives that — what you lose is the review's text as a record the next round can read. And the command needs the `DEEP_REVIEW_SKILL=1` prefix, or `guard-no-reviewer-reply.sh` denies it as a top-level comment.

  For a safe fallback, post the reviewer's own file rather than retyping the review: the review has already cost one copy in your context, and writing it back out costs another. Decide from the file at the round's own `/tmp/deep-review-marker-<pr>-run<N>-<short-sha>.md` path, whatever `MARKER-FILE:` says, since a missing or wrong `MARKER-FILE:` doesn't mean nothing else is at that path. The path alone can't tell your reviewer's file from a peer loop's on the same round and head; the header can, so check it first. If a file is there and its `<sub>` header line isn't your reviewer's `MARKER-HEADER:`, another reviewer of this round wrote it: stop and report a peer loop (an escalation, below) without starting the addressing pass, and don't rebuild over it or post it, even when it is malformed too. If the header matches, `review-loop-state --check-body <file> --expect review` passes, and the file carries the section headings `deep-review`'s format calls for, that file is the one to post; the check refuses a body opening with the response marker too. `--check-body` never looks for those headings, so check them yourself: a file that lacks them is the same file step 2 refuses as the review. Rebuild the body yourself only when no file is there, or the header matches and the file fails `--check-body` or lacks those headings: at the round's own path, in one overwriting write, as its own tool call, then check it the same way. Finish the SHA and tree checks, then run the exact standalone `--body-file` command from `deep-review` in a separate shell call, with no `cd` before it and nothing chained after it. This gives a read-only reviewer a writable parent credential, and corrects a distinguishable noncanonical attempt once. **If that fallback is denied, make the round write-stopped.** Don't reorder its flags, switch back to a heredoc, or attempt the address response through the rejected shape. Keep the full review and eventual response in the next reviewer's prompt and in the final handoff instead. A deterministic guard denial does not become transient because the loop has another record to post.
- **The posted marker holds exactly one review.** Re-read it through `review-loop-state <pr> --repo <owner>/<name> --json` and require `latest_marker_top_level_markers` to be `1`. More than one means an older body got into this round's file and the comment carries earlier rounds after its own `</details>`; `null` means no marker posted. Don't post another comment to repair a bad one, and don't edit it — say in the response comment that the record is corrupt, feed the next reviewer this round's review from the round's body file when it passes `--check-body` and carries those headings, or otherwise from the first review in the marker, and file the recurrence. Apply the same check to every response comment after it posts, with `latest_response_top_level_markers`.
- **HEAD is the SHA you recorded, and the working tree is clean.** Check both. The tree catches a probe the reviewer didn't restore; the SHA catches the failure that matters, because **a reviewer that commits its own fix leaves a perfectly clean tree.** Expect the tree half to be quiet in practice — auto-review declines most in-place mutations, so reviewers probe in a throwaway clone, except where the suite needs the real tree — and the SHA half to be the one doing work.
- **Know where the guarantees stop, and don't try to enumerate them.** This check sees the tree and HEAD, so it catches a commit. Everything a reviewer could do to the PR itself — merge it, mark it ready, close it, retitle it, change its labels, edit its body over the API, even delete the remote branch with an ordinary push — moves neither, so the prompt telling it not to is the entire defence. The hooks stop some of those on some paths and none of them on all paths, and that boundary moves whenever a hook changes, which is why the mechanism is the thing to remember rather than the list.
- **If the tree is dirty, the discriminator is whether it looks like a probe.** A probe — a gutted function, an emptied file, a flipped constant in a file the review discusses — you restore before touching anything, because addressing findings on top of a mutation is how you commit one. Anything else is somebody's in-flight work: leave it exactly as it is, don't restore or stage it, and surface it. Same if HEAD moved.
- **Treat the review's evidence as claims, not transcripts.** Only the reviewer's own text reaches you, on the PR or in its final message, so a measurement it describes is unfalsifiable from where you sit — and a plausible-looking block of command output may be a summary written to look like one. Re-run anything a finding turns on; that is how each round here has found the previous round's mistakes.
- **If neither the final message, a marker, nor a passing body file at the round's path carries the review, that round didn't happen.** Re-dispatch at the same round number rather than addressing what you can remember of it. Each of those three is a fallback for the others, so losing all of them is the one case where there's nothing to work from.

### 3. Address the findings

Follow `address-deep-review`. It owns the triage — which findings to take, which to decline, the acceptance rate you state every round, the second-order sweep, and the response comment. Don't re-derive any of that here. The one thing restated below is the stopping rule itself, because deciding when to go again is this skill's job rather than the addresser's.

Seven things this skill adds on top:

- **Check for a peer's response before addressing and again right before posting yours.** Run `review-loop-state <pr> --repo <owner>/<name> --json` before the addressing pass starts, and again after your push and before the post. `latest_run_responded` describes the run numbered `rounds_complete`, which isn't always the run you're answering, so compare the two first. If `rounds_complete` is larger than your run, some comment's own header names a later run than yours; if you didn't post it, a round exists that you didn't dispatch, so treat that as a peer loop. If it is smaller, this run's marker didn't post, and the boolean refers to an earlier round's response, probably your own. Read it as a peer signal only when the two are equal. In that case `true` means another session already answered this review. If that response's header names the same run and head, stop and report a peer loop (an escalation, below): before addressing, don't start; before posting, don't post. Otherwise write the response body in its own tool call, at `/tmp/address-deep-review-marker-<pr>-run<N>-<short-sha>.md` as one overwriting write, and post it with the exact standalone `--body-file` command from `address-deep-review`: no `cd` before it, nothing chained after it.

  A note added to a response after it posts, such as marking it superseded, goes at the end, as prose. `review-loop-state` reads three things off a body, and each turns a misplaced note into a false record. A line above the token makes the comment count as nothing. A line starting with `|` is parsed as a finding row, so a correction that restates a row records a second outcome for that finding, and a restated must-address decline blocks the stop. A marker token alone on its own line makes the record read as corrupt.
- **Check that the PR is still open right before every push, chained into it.** Run `review-loop-state <pr> --repo <owner>/<name> --require-open && git push …`, so the push runs only if the check passes. Any non-zero exit means don't push: 3 means the PR isn't open (an unknown state refuses too), and 1 means its state couldn't be read. The chain narrows the window between check and push, but can't close it. A merge deletes the head branch, so a push after it creates a brand-new ref with no PR, and git reports success: on PR #137 a second addresser's push re-created the merged branch 20 minutes after the merge, and the work looked unlanded. On a refusal, don't push and don't post the response: keep the commit, and report its SHA and the PR's state (or, on exit 1, the error it printed) in the final report so the owner can decide whether the fixes need a follow-up PR.
- **A write-stopped round is still addressed, but not commented.** Complete the triage, checks, commit, and push as usual, then retain the response body instead of posting it. Paste the full review and retained response into the next reviewer's prompt; if the loop stops or escalates before another round, put both in the final handoff.

  **Keep a durable copy of both, because the PR never gets one.** `/tmp` is the only other home a write-stopped round's records have, and a reboot or tmp reaper clears it, leaving a resuming session with a gap at that run and nothing to fill it. As soon as the response is retained, before you dispatch another round or write the final handoff, copy both under the clone's common git dir, naming the loop's tree explicitly (`$WT` in local-config, the claimed slot in Substack) because this loop's shell is usually sitting in `/tmp`: `D="$(git -C <tree> rev-parse --path-format=absolute --git-common-dir)/deep-review" && mkdir -p "$D" && cp <review-file> "$D/<pr>-run<N>-review.md" && cp <response-file> "$D/<pr>-run<N>-response.md"`. Keep `--path-format=absolute`: from a main checkout, `--git-common-dir` alone prints a relative `.git`, which resolves against the shell's cwd rather than the tree. That directory is shared by every worktree of the clone, is never tracked, and is outside the clean-tree check. Name both paths in the next reviewer's prompt and in the final handoff, and a session resuming this loop reads them there for any round the PR doesn't show. It only helps a resume on the same machine: in a cloud session the clone's common dir dies with the container, so there the handoff text is the only copy. Remove a PR's files once that PR merges or closes, and not before, since a capped or paused loop can still resume.
- **You are the author as well as the addresser**, which biases you in a direction the addresser alone isn't. You know what you meant, so a finding that misread the code reads as simply wrong — when often the code is what misled it. When you're about to decline on "that's not what this does", ask what the reviewer was looking at when it concluded otherwise.
- **Expect a mid-loop commit to carry the must-address and should-address findings and little else.** `address-deep-review` routes `consider` findings to the tracker, so a round that files four and commits two is working, not shirking.
- **Report each round as it lands** — round number, findings, taken / settled / declined (plus taken in part or out of scope when any row is, and deferred on a round that escalated, as address-deep-review's header counts them), and the SHA you pushed or `none`. One line, no question attached.
- **Delegating the addressing pass to a subagent is allowed**, and on a large repo it is often the only way to finish. The separation this design depends on is reviewer ≠ author; handing the addressing work to a subagent doesn't weaken that, because the subagent is still not the reviewer. Do it when a review comes back several thousand words and you can see the context running out. It buys less than it looks like it will — one loop delegated every addressing pass and still escalated on context at round 2 of 5 — so treat it as a way to get further, not as a fix for starting the loop in a spent session.

  Hand it the marker comment's URL to read the review from. When the marker didn't post, hand it the round's body file path instead, once step 2 has accepted that file as the review, so the review doesn't pass through your context a second time; hand over the review in full only when step 2 accepted none. Then add `address-deep-review`, the repo path, the PR number and the round number, and the SHA you recorded. From a `local-config-worktree --review` tree also hand it the PR's head branch and the push command, `git -C "$WT" push origin HEAD:<head-branch>`: its default `git push -u origin HEAD` succeeds from `review/pr-<pr>` by creating a new remote branch, and the PR never moves. The number and the round matter because its response header is `responded to run N`, which is what `review-loop-state` counts — a subagent left to work either out is counting rounds by hand, which this section already forbids. Say the response comment is its job unless the round is write-stopped; then retaining the complete response body is its job instead. That skill puts the comment, the acceptance rate and the second-order sweep on "you", and a delegated pass silently owns all three. The author bullet above is the one that doesn't transfer, and that cuts both ways — a subagent carries none of your bias toward the code, and none of your knowledge of what you meant by it, so a finding that turns on intent is worth resolving yourself before you hand the rest over. When you rule on, or relay a ruling on, a finding that offers alternatives, quote the option you chose from the review verbatim, and name what must not change. A restated option lets a second, unrequested change in, since the subagent can't tell your gloss from the finding. A quote alone isn't enough either: one loop ruled "TAKE the first option — normalize an empty-or-contentless doc to `EMPTY_DOC` in `docForEditor` and refuse only unknown node/mark types", word for word from the review, and the addresser read "refuse only" as licence to delete the `.check()` content check. The next round found that deletion was a defect; naming `.check()` as unchanged would have stopped it. Run it in the foreground, for the same reason the reviewer runs there: a backgrounded addressing pass ends your turn mid-round.

  On return, read the response comment it posted — or the complete retained response on a write-stopped round — and the SHA it pushed rather than its account of them. Step 2's HEAD check inverts here, because this subagent is *supposed* to have moved HEAD, so that comparison belongs to step 4 instead. The tree half still holds: it committed and pushed, so anything left dirty is residue.

  **When the subagent was interrupted before it committed, its residue is resumable, but only after two checks.** First confirm HEAD and the remote head are both unchanged since you dispatched it, and that the subagent has actually stopped. Then read the whole residue, not only `git diff`: `git status --porcelain` for staged and untracked paths, `git diff HEAD` for every tracked edit, and each untracked file in full. Confirm it touches only what the review's findings name. If both hold, hand the diff to a fresh addressing subagent as part of the same round, saying it is a partial pass to finish and verify, not a finished one. Edits you can't trace to that subagent, or edits that come back after you've checked, are somebody else's work, and the rule above for a dirty tree applies unchanged. On PR #420 an interrupted round-4 addresser left two edited files and no commit, and checking the head and reading the diff was what made them safe to resume.

### 4. Decide whether to go again

> **The loop ends on a round that produces no commit** — every finding declined, already settled, or fixed somewhere that isn't the diff — with local checks and CI green on that head.

That's the whole stopping rule, apart from a round 1 posted with a wrong must count, which goes again (below). What it's really testing is that the head the reviewer examined is the head that will merge — no commit of your own is the common way that happens, but it isn't the same statement, so check the SHAs rather than inferring it. The certification comes from the reviewer, on the final state, and any round that produces a commit invalidates the review that prompted it.

- **Commit pushed → go back to step 1** with the round number incremented.
- **You moving the head for any other reason counts as a commit too.** A rebase onto a fresher trunk is the case that comes up — sometimes you need one mid-round just to get the suite running, so it isn't avoidable — but it replaces every SHA the reviewer read, which is exactly what the test below is looking for. Don't reason that it "wasn't a fix" and stop anyway. Rebase through [`refresh-stack`](../refresh-stack/SKILL.md) rather than by hand; it pushes a lone branch as a stack of one. Then verify the rebase preserved the diff by diffing the head it pushed against the pre-rebase tip across the PR's own files, which is [`merge-stack`](../merge-stack/SKILL.md)'s tip-vs-tip step; it also carries the two things that make the result readable — it is expected to be empty or trivially explainable rather than literally empty, and on a branch whose conflicts you resolved the diff can't be the gate at all. A hand-typed `git push --force` or `--force-with-lease` on a branch under review is denied by `guard-force-push.sh`, and the denial is right, so don't look for another way to force it. Then say in the response comment that you rebased and why, and treat the round as commit-producing.
- **A round 1 posted with a wrong must count → go again**, even with nothing pushed (step 1's post-fold check). `review-loop-state` reads that header's must count as the floor on the response's must-address rows, and it is the only check that the response kept one for every must-address finding: a response that drops one still stops clean under a header that undercounts it. Round 2's own header replaces it.
- **Push rejected → escalate.** `Pushed: rejected` means fixes exist that the reviewed head doesn't carry, so it is never a clean stop, however unmoved the head looks.
- **Nothing pushed → compare the SHA you recorded at dispatch against the PR's head now** (`review-loop-state <pr> --recorded <sha>` does it, and reports `moved: no` in text and `head_moved: "no"` in `--json` when they match; at any round it also reports `clean_stop: true` in `--json` and `-- stopped clean, no further round` in text when this stop applies. Below the cap it also needs nothing on the PR to hold it: the latest response defers nothing and its header names no escalation, and no response declined or deferred a must-address. When only those hold it, `--json` reports `held_stop: true` and lists each one in `held_by`, the text reads `-- no commit at the recorded head; escalate or check declines before stopping clean`, and the escalation list below decides. The script can't see an author's ruling, so read the rulings first: an item already ruled on clears, as **An escalation clears once the author has answered it** says. At the cap `clean_stop` is `stopped_clean`, which the cap bullet covers. It can't see CI either, so check that yourself). Equal means the head the reviewer was pointed at is the head that will merge, so stop — unless round 1 was posted with a wrong must count, which goes again (above) even when `review-loop-state` reports `clean_stop: true` — and don't dispatch another reviewer against it, since reviews aren't deterministic and re-reviewing an unchanged head produces a different list and restarts the cycle for nothing. Different means something else landed during the round — the user pushing, a base merge, another agent — and you'd be certifying a head nobody read, so go again. `review-loop-state` normalises for you: a recorded SHA is usually short — comment headers carry nothing else — and it matches any abbreviation of seven characters or more against the full head. Below seven it answers `unknown` rather than guessing, because that is shorter than git would resolve either. **Treat `unknown` as moved**: it means the comparison did not happen, and stopping on a comparison that did not happen certifies a head nobody read. Re-record a longer SHA and ask again if you want the real answer. Don't normalise by hand with `git rev-parse`: handed a short SHA it doesn't have locally, it exits with `fatal: ambiguous argument` and prints the input back, which reads as success. If it reports PR metadata synchronizing, it prints `(moved: unknown)`, and that `unknown` is no answer either: wait and re-run as step 1 says before you stop or go again.
- **Use the SHA you recorded, not the one in the marker header.** The header looks like the authority on what was reviewed and isn't: `deep-review` fills it from a live read of the PR's head at the moment it posts, so if the user pushed mid-round the header carries the *new* head. It would agree with the post-push head and hide precisely the case this test exists to catch. The recorded SHA is the one you observed yourself, and it still exists when the marker never posted at all.
- **Never substitute your own memory of whether you pushed.** "I didn't commit anything" is a claim about you, not about the head.
- **CI: check it on the terminating round, not on every round.** Mid-loop it's wasted wall clock, because the next commit invalidates it anyway. **Zero required checks is a pass, not a wait** — `gh pr checks` exits non-zero when a repo reports none at all, which is the normal case wherever workflows don't run on PRs, and reading that as "not green" holds a stop that can never clear. Where there are no checks, the local ones carry the signal.
- **Red CI that the base shares is not this head's red.** When checks exist and fail, "green" means the head adds no failure of its own: compare the whole failing set on the head against the latest run on the base, down to the failing suite and assertion where the logs show them. **No failure outside the base's set is a clean stop**; name the failing check and the base run you compared against in the final report, and lean on the local checks for the signal the red job can't give. **Any failure outside the base's set is the head's**, even when the head also fixes one of the base's, so treat it like any other finding, or escalate below when it is outside the diff. On a round that pushed nothing, run this comparison before you post step 3's response so the response can name it too; if the response is already up, the comparison goes in the final report and, if anywhere on the PR, in a trailing prose note, never a `|` row. Two shapes need a read before you compare:
  - **A job that finished in seconds with zero steps never started one.** `gh run view --log-failed` answers `log not found` because there is no log. List recent runs on the base and look for any success at all: none means the account or the runners are failing, not the code, so it is base-identical red and the same clean stop applies. When a queue profile lists a CI exception for it, `steward-task-queue` section 9's stricter recognition test and local fallback govern instead.
  - **A merge-window gate isn't a check of the head.** A check that fails on the clock rather than the code, such as a code-freeze check like `buildkite/substack-code-freeze`, says nothing about what the reviewer read. Read the failing log line before counting it; if it is the gate's message, it doesn't block a clean stop. Name it and leave the re-run or the override to the author.
- **Round cap of five, then hand back.** The cap only overrides a verdict that would otherwise continue — a fifth round that reaches a clean stop stops clean rather than being escalated for having taken five. `review-loop-state <pr> --recorded <sha>` tells the two apart: it prints `AT CAP -- stopped clean` and reports `stopped_clean: true` only when the capped round's response records `Pushed: none`, leaves no must-address row open, and the head hasn't moved from the SHA you recorded. Open means any outcome but `taken` or `settled`, so `deferred` and `declined` rows hold the stop. Markup in the severity cell doesn't hide a row, and the stop also fails closed when the response parses as fewer finding rows than its header's `N findings`, or fewer must-address rows than the run's marker counts. That count is the original `<sub>` header's alone, so a must-address finding only a folded duplicate raised is yours to carry into the response; a doubled round 1 rewrites that header to the union (step 1). Before the capped round has a response it prints `AT CAP -- no further rounds; stop clean if this round pushes nothing, otherwise escalate`, because the verdict doesn't exist yet: re-run it after the response posts. If the head has already moved from the SHA you recorded it prints `AT CAP -- escalate (head moved)` instead, and if the comparison didn't happen it says to escalate unless a re-run reports `moved: no`. Every other capped state prints `AT CAP -- escalate`. `stopped_clean` leaves out the below-cap holds, so a decline the author has already ruled on doesn't hold it at the cap or in certification; one nobody has ruled on is still the escalation list's to catch. Below the cap it is always false, so read `clean_stop` there. `address-deep-review` has the cost argument behind the number.
- **At the cap, a real finding that isn't must-address gets filed, not fixed.** The terminal round's awkward shape is no must-address findings sitting beside a handful of one-line defects that are genuinely worth having, including one the reviewer says it would take first. Take any of them and you ship a head nobody has read, with no round left to read it — so file them and hand them back, and say in the response comment that you did. Remember what the size of those edits is worth: "small and safe" is exactly what an addressing pass's own injected defects look like from the inside, which is the reason this loop has rounds at all.

**The reviewer's own another-round verdict is advisory.** It sits at the top of the marker header, in plain English, written by the agent that just read everything — and this test decides anyway. A reviewer's all-clear is not a stopping criterion: the case this whole design is built on is a round whose review said no further round was needed, followed by one that found a reachable must-address.

Note what the rule does to over-compliance: an addresser that takes every finding commits every round, so it can never terminate. That's deliberate. It converts the quiet failure of agreeing with everything into a visible non-terminating loop.

## Certification after a cap handoff

A loop that reaches the cap on a commit-producing round hands back a head nobody reviewed. The cap still forbids another fix-and-review cycle, but that head gets one independent read before merge, as a certification pass. Run one only when both of these hold:

- **The previous loop hit the cap and said its last pushed head was unreviewed.** Its final response names that head and escalates at the cap: `review-loop-state <pr> --repo <owner>/<name> --json` reports `latest_response_pushed` as that head's SHA — not `none`, `rejected`, or `null` — and `stopped_clean: false`. The pushed value comes from the response itself, and anything but `none` makes `stopped_clean` false, so this needs no SHA recorded by the earlier loop.
- **Someone explicitly returned that head for certification.** Either the author asks for certification of that head, or the queue moves the issue back to `Needs review` with a comment naming the head and the word `certification`, as `review-task-queue` section 9 writes it, or a `Decision:` record written under `review-end-decision` returns that head for certification. A handoff you read as implied permission doesn't count, and neither does a newer head: if the head moved since the handoff, the certification request is stale, so report that instead.

The pass is one fresh reviewer, dispatched as in step 1 with the next run number and the prompt's certification line, so its header reads `re-ran (run N) certification` with the run token first. `review-loop-state` reads that shape as `certification_run: N`; the older `(run N certification)` shape names no run at all, and a comma-noted `(run N, certification)` names run N but not a certification. Then:

- **It is read-only.** Don't address findings and don't move the head: no commit, no rebase, no push.
- **A clean pass completes the review.** A clean pass has zero findings. Post a response with `Pushed: none` and no finding rows, whose header reads `responded to run N (<sha>) certification`. `review-loop-state --recorded <sha>` then reports `stopped_clean: true`; any finding row in a certification response keeps it false. The response header's `certification` is enough on its own to apply that rule, so a missing or reshaped certification marker doesn't switch it off. The queue moves that exact head to `Ready to merge`.
- **Any finding is deferred.** Record every finding as `deferred` in the response, file it or hand it to the author, and stop. Certification never turns into a sixth addressing round.

## Escalate instead of continuing

Eight conditions end the loop early. Each one ends your turn unless `review-end-decision` continues the loop through its extension round or an upheld adjudication: say which fired, report what the loop did, and stop.

**"Stop" means after the current round's addressing pass, not instead of it.** A round is a review plus an addressing pass, so a condition that fires once the review has landed leaves findings sitting unaddressed — and "stop now, leave them" and "finish addressing, then stop" are both readable in a bare "stop". Finish the pass — or the rest of it, for a condition that fires part-way through one — then stop; that is the same round boundary the context condition below means. The head that pass ships is by definition unreviewed, so say what went into it when you hand over. Two of these conditions trigger on an inability to do the work this is asking for, so if it's context you're short of, delegate the pass (step 3) rather than skipping it.

There are two exceptions, and both stop without addressing because finishing the pass would push onto work whose ownership or shape is the open question you're handing over. One is a pivot verdict that `review-end-decision` rules real: finishing the pass means committing and pushing onto code whose shape is the open question. The other is a peer loop found before the addressing pass starts, by step 2's marker-path check, round 1's pass-file, fold-file or post-fold check, or step 3's check before addressing: finishing the pass means committing and maybe pushing onto a branch another loop is also addressing. In both, say what you left unaddressed.

**Stopping on a pivot without addressing is not stopping without checking.** Escalating forfeits every round that was left, and a pivot can arrive in round 1, which spends the entire budget — so verify what the different-approach section rests on before you put it in front of the author, exactly as step 2 says to for any finding. A pivot argued from a mechanism that doesn't hold, or from a repo state that has changed since the reviewer looked, is a finding to answer in your response comment rather than a decision to hand over. Then run `review-end-decision`'s pivot tests before you stop or record anything. A pivot they rule not real doesn't stop the round: address it normally and decline the pivot with the evidence. Only for a real pivot, record the outcomes as `deferred` rather than `declined`; `address-deep-review` owns why that word and not the other one.

**Escalating ends the loop, not the decision.** Before you report, follow [`review-end-decision`](../review-end-decision/SKILL.md) for whichever condition fired. It decides what this file used to leave to the author: certify, take its one extension round, adjudicate a declined must-address, close and re-scope, or stand down to a peer. Report a condition as the author's only when that skill lists it under "What still needs a person". Two places in this file yield to it. Its extension round is the one exception to both the cap and certification's no-addressing rule. A certification whose findings include no must-address is a clean pass once those findings are filed and the head adds no failing check outside the base's set, as that skill says. Their rows stay `deferred` as recorded here, and its `Decision:` record names the filed items.

- The round cap is reached, and `review-loop-state` doesn't report `stopped_clean: true`.
- **A peer already responded to this run, or is ahead of it.** Step 3's check, before addressing or before posting, found a response for this run and head that you didn't post, or a marker or response you didn't post whose own header names a later run, or a second marker for the run you are answering that your reviewer didn't write. Step 2's header check finding another reviewer's file at this round's marker path is the same condition. So is round 1's pass-file check finding a file none of this session's passes wrote, its fold finding a file it didn't write at that path, or its post-fold check finding a duplicate marker. Don't post yours, and don't push further: report both responses, and the SHA each pushed — or for step 2's case, both headers — and let `review-end-decision` decide which controller owns the loop; for queue-owned work that is the current Claim holder.
- **Fixes were taken but not landed.** The push was rejected, so the response records `Pushed: rejected` and the patch goes to the owner. Nothing moved the head, but the reviewed head isn't the one with the fixes.
- **Any must-address finding recorded as declined or deferred in any response comment on this PR**, checked at the point where the round would otherwise stop clean. Declining one without a reproduction refuting it is forbidden outright, so that case never reaches here; declining one *with* a reproduction is legitimate, and still can't be the thing that ends the loop, because in a single session the addresser writing that reproduction is also the one grading it. Escalating the moment any must-address is declined would instead forfeit the remaining rounds over one refutable claim out of a dozen, and closing the "decline everything" exit doesn't need that: a round that declines everything produces no commit and would stop clean, which is exactly when this fires.

  **`review-loop-state` reports these as `declines to check`**, not as a blocking verdict. Its JSON `must_address_declines` worklist carries the round, normalized outcome, and whether a later response mentions that finding number; `blocking_must_address` remains as a compatibility alias. A decline from round 2 still appears in round 5, so use the worklist rather than recollection or header counts. It can't tell a ruled-on decline from an open one, so below the cap `clean_stop` holds while the worklist is non-empty and `held_by` names each decline, and an author's ruling is yours to read. The worklist leaves out `deferred` rows, and so does the cap's `stopped_clean` once a later response becomes the latest; below the cap `held_by` names them. So before stopping, also read every response comment for must-address rows whose outcome is `deferred`, and treat each one as this condition, like a decline.

  Record a partly-refused must-address once, with `taken in part`, `half-taken`, or `declined` as the outcome. The tool reads that leading outcome phrase and ignores words such as "half" later in a taken row, so a duplicate declined row is no longer needed to keep the refusal visible.

  **An escalation clears once the author has answered it.** This condition names a state, and left alone a state never resolves — one partly-refused must-address in round 2 would otherwise block a clean stop on that PR forever, including for every later session. So a decline that a previous escalation already handed over stops counting once the author's ruling (including one an agent relays as a decision from the author), or a `Decision:` record written under `review-end-decision` that rules on it, is recorded on the PR. A `Handover:` record rules on nothing, so it clears nothing. **When a response row sends the remainder to a tracker issue, read that issue's whole thread as well, not only its latest comments.** The ruling can land there instead of on the PR, under later claim and triage comments: on PR #621 the author ruled on the filed remainder in its issue, and the loop's final report asked for that ruling again an hour later. The same bar applies there as on the PR: the author's ruling, including one an agent relays as a decision from the author. A `Decision:` record lives on the PR, as `review-end-decision` says. Agent triage that sounds like a decision is neither. Such a ruling on that issue counts, and the final report quotes it rather than asking again. What escalates is the finding nobody has ruled on yet.

  A later mention is a triage clue, not a ruling. Decide whether the author has already answered each worklist row before escalating; finding numbers are round-scoped, so a later row with the same number does not clear it.
- The review's Step 2 concluded the change should pivot. `review-end-decision`'s pivot verdicts decide whether a different-approach finding is real.
- A must- or should-address finding you can neither reproduce nor refute. A `consider` one goes to the tracker as `declined` instead, as `address-deep-review` says, and escalates nothing.
- CI fails something the base doesn't, for a reason outside the diff — a flaky suite, a missing secret. A base that is red the same way is step 4's clean stop, not this.
- **You're running out of context** — the one condition particular to running this in a single session. Every round adds the reviewer's index, the findings you opened, and the addressing work to this conversation, and on a ~200k window five rounds of that is a lot. Stop at a round boundary and hand over: the PR's markers and response comments hold the entire state of the loop, so a fresh session picks it up at the next round with nothing lost.

Uncommitted work you didn't make is the other reason to stop, and it isn't on the list because it can turn up at any point rather than at a round boundary. Step 2 has the discriminator; what's specific here is that you must not hand a reviewer a tree containing it, because its probes would measure that work alongside yours and its restore could revert it.

## What stays the user's

**Stopping is not merging.** The loop drives a PR to a defensible stopping point and says so. Don't mark it ready, don't merge, don't touch labels, don't force-push, and don't reply to a human reviewer other than the user. Report the stop, the round count, and the PR URL.
